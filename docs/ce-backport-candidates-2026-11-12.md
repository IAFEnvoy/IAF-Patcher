# IceAndFire-CE → IAF-Patcher 修复迁移评估

审查日期：2026-11-12。本轮只分析迁移价值并保存报告，没有修改生产代码、运行游戏、提交或推送。

## 结论与范围

有多项值得迁移。优先处理网络校验、AI 搜索和龙锻炉，再处理图鉴/石像渲染及鸡蛇权杖。这些问题在 IAF-Patcher 实际依赖的原版 Ice and Fire 中仍能找到对应错误路径，现有补丁没有覆盖。

本报告是候选修复的跨版本核对，不是对 IAF-Patcher 或原版模组的完整审计。结论来自目标 JAR 的反编译控制流、Minecraft 调度实现和现有补丁的对照；“确认存在”指静态实现存在相应缺陷，不表示已经在四个版本中逐一进游戏复现。

- 目标：`E:/Java/IAF-Patcher`，`stonecutter` 分支，提交 `1b8c9b78c39abcfdb2b59276f995f79e180c5514`，Patcher 1.3.1，四个 Forge 目标。
- 迁移来源：CE 1.20.1 修复提交 `8dbab70a`；另外参考 master 的 `8c62ad53`（#292）和 `7ae3fcc3`（#285）。没有切换任何工作区分支。
- 检查了 Patcher 全部现有 Java 补丁、Mixin 配置/插件及版本依赖；从每个目标依赖提取网络处理器、全部 AI 和相关实体/方块/物品/渲染类，使用 Vineflower 1.12.0 还原控制流，并补查四版 Minecraft 的 Mob/Goal/GoalSelector。
- 所用原始 JAR 与映射 JAR 的路径、SHA-256、逐版本关键代码证据见 [证据清单](ce-backport-evidence-2026-11-12.json)。未把 CE 的 GameTest 结果当作 Patcher 的测试结果。

### M01：多部件攻击与九头蛇索引

四版的 `MessageMultipartInteract.Handler` 都在距离小于 100 格时直接使用包内正浮点伤害；`MessagePlayerHitMultipart.Handler` 同样只限制 100 格距离，就调用 `player.attack`，随后保存包内九头蛇头索引。没有充分证明目标就是合法部件对应的父实体，也没有正常近战命中校验。

四版 `EntityHydra.hurt` 仅处理 `lastHitHead > getHeadCount()`；负值没有防御，等于最大头数时也有数组边界风险。1.20.1 的关键点为 `MessageMultipartInteract.java:44`、`MessagePlayerHitMultipart.java:49`、`EntityHydra.java:373` 和 `:485`。

应同时补齐服务端目标/距离/可见性/伤害来源校验及实体内部索引防御。CE 新版直接停用旧通道、改走原版部件交互的方案不能原样照搬：Patcher 需要照顾原版客户端正在使用的旧消息，否则会使部件攻击或交互失效。迁移时必须对合法原版客户端完成兼容回归。

### M02：乘骑包有实质性的版本差异

| Minecraft | 仍写入包内坐标的实体 |
| --- | --- |
| 1.16.5 | 龙、鹰马、海马、死亡蠕虫、羽蛇 |
| 1.18.2 | 死亡蠕虫 |
| 1.19.2 | 死亡蠕虫 |
| 1.20.1 | 海马、死亡蠕虫、羽蛇 |

四版都需审视递归乘客关系是否足以授权控制；应区分实际控制乘客与主人肩上的幼龙，并过滤无效控制位。1.20.1 的海马和羽蛇 `setPos` 位于主人校验之外。

实施时分别处理 C2S 服务端控制和客户端同步用途；不能把所有方向的包一起取消。先确认删除 C2S 坐标写入后原版载具移动、升降与下坐骑仍正常。

### M03：旧三版仍普遍缺少 enqueueWork

1.16.5、1.18.2、1.19.2 的 `MessageDragonControl`、`MessageMultipartInteract`、`MessagePlayerHitMultipart` 等直接在处理器中操作实体。1.20.1 这几条已经调用 `enqueueWork`，不应重复包一层作为同一项修复。

1.20.1 仍有 `MessageSwingArm.Handler.handle` 直接调用 `ServerEvents.onLeftClick`，后者可生成幽灵剑实体，值得补齐游戏线程调度。`MessageSetMyrmexHiveNull` 也没有排队，但这里只是代理字段重置，风险和实体生成不同，不应把“未发现 enqueueWork”的文本匹配数算成 bug 数。

补丁应在网络线程解码后排队，进入游戏线程后重新取得发送者和目标，再做 M01/M02/M04 的校验。Mixin 的外层 Handler 与 lambda 形状在几个版本中不同，需要逐版选注入点。

### M04：讲台需要覆盖自定义消息入口

四版 `ContainerLectern.clickMenuButton` 都先访问 `possiblePagesInt[id]` 再钳制编号；`getPossiblePages` 把上界钳为数组长度，仍允许越界；`TileEntityLectern.stillValid` 恒为 true。非法按钮的越界发生在到达相关分支时，不能描述为所有生存玩家请求都会在同一点崩溃。

原版还有独立的 `MessageUpdateLectern` 解锁请求。以 1.20.1 为例，`handlePacket` 检查区块存在和方块实体类型后，就可按包内页编号更新图鉴，没有要求当前打开该讲台菜单、处于交互距离、请求页是当前可选项，并在同一服务端事务中验证和消耗手稿。单独移植 CE 的菜单数组检查不够。

建议将按钮范围、有效页、菜单/距离/BE 身份、手稿消耗与页解锁统一为服务端校验路径，同时保留旧客户端所需的协议。

### M05/M08：锻炉建议作为一个行为单元移植

四版都存在以下对应路径：

- `tick` 用旧的 `prevAssembled` 调用 `setState`；核心启停方向错误。
- `BlockDragonforgeCore.setState` 每个分支重复设置同一个方块；虽然切换时设置 `keepInventory`，`onRemove` 没有据此区分同种核心切换，仍掉落库存并移除 BE。不能仅设置该静态字段就认为库存已保护。
- `isBurning()` 依据 `cookTime > 0`；停火时先减进度，后续又因“正在燃烧”加回来，进度可卡住。
- 合并产物只比较物品身份；相同物品、不同 NBT 的输出可能混堆。空输出槽容量也应依据真实配方结果的最大堆叠数。
- `DragonForgeRecipe.assemble/getResultItem` 返回同一 `result` 对象。应返回副本，并确认 JEI 和配方调用者的契约。
- 保存 `CookTime` 前强转 short；余热倒计时没有完整保存，若干库存/进度变化缺少标脏。

在 1.20.1 中可复核 `TileEntityDragonforge.java:65/:205/:214/:255`、`BlockDragonforgeCore.java:46/:120`、`DragonForgeRecipe.java:71`。旧版 1.16.5 的 tick 是实例方法，之后是静态 ticker，不能共用同一回调签名。

CE 的 F02“输入口永久保留旧核心”需要降低表述：原版四版 `BlockDragonforgeInput.neighborChanged` 已调用 `resetCore()`，正常邻居更新有主动失效路径。仍可补上核心龙种、是否移除和 BE 身份验证；当前查找只认 BE 类型，可能选到不匹配龙种的相邻核心。不要把 CE 的旧引用结论整条算作新增已确认问题。

### M06：搜索冷却应覆盖原版额外 AI

1.18.2～1.20.1 的 Minecraft `Mob.serverAiStep` 根据服务器 tick 与实体 ID 的奇偶交替调用完整 GoalSelector 和仅运行中的 Goal。部分实体的 `canUse` 可以一直错过 `gameTime % 4 == 0`，初始空列表之后不再更新。这是调度相位问题，不是需要把搜索范围缩小的问题。

已找到使用该门槛的 Goal 数量：1.16.5 为 12 个，1.18.2 为 11 个，1.19.2 为 11 个，1.20.1 为 10 个，完整名称在证据 JSON 中。

1.20.1 的 10 个为：`AmphithereAIFleePlayer`、`AmphithereAITargetItems`、`CockatriceAITargetItems`、`DragonAITargetItems`、`DreadAIRideHorse`、`PixieAIFlee`、`PixieAIPickupItem`，以及 CE 现有七项之外的 `MyrmexAIFindMate`、`MyrmexAIForageForItems`、`MyrmexAIPickupBabies`。1.18.2/1.19.2 另有 `HippogryphAITargetItems`，1.16.5 再有 `DeathwormAITargetItems`。

1.16.5 的 `MobEntity.serverAiStep` 每 tick 执行完整选择器，不具备这里同样的奇偶锁死条件；可统一改成截止时间以分散查询，但不应宣传修复了同样的永久失效。

建议迁移 CE 的每 Goal 独立截止时间，按实体 ID 错开首次搜索，处理时间回退，保留搜索间隔。不要每 tick 强行搜索，也不要在所有实体上设置同一个固定相位。

### M07：小而明确的 AI 修复

四版均确认：

- `DragonAITarget.canUse` 要求 `target != null` 才调用父类搜索，新的 Goal 因目标尚未初始化无法进入搜索。调整调用顺序时须保留体型、主人、龙种、阵营条件，避免父类搜索被调用两次。
- `DragonAIMate` 保留 `continueExecuting()`，没有覆盖实际的 `canContinueToUse()`。Minecraft 默认实现会重新调用 `canUse`，不保证执行预期的伴侣存活/繁殖延时限制。应新增正确的覆盖，而非注入一个目标类本来就没有声明的方法。
- `EntitySheepAIFollowCyclops.canContinueToUse` 在独眼巨人存活时返回 false；`PixieAIFlee` 在接近终点时才继续，方向写反。
- `EntityAIWatchClosestIgnoreRider` 的观察者字段没有赋值，乘骑过滤条件也与“忽略骑手”目的相反。

这些是现有鹰马巡游补丁之外的行为，适合做独立、小范围的 Goal Mixin。

### M09：权杖要按版本区分数据实现

四版 `ItemCockatriceScepter.specialWeaponDmg` 都位于注册表 Item 单例上，玩家之间会共享累计；`getUseDuration` 都返回 1。值得迁移服务端按当前使用栈扣耐久、合理持续使用时间，以及停止/破损时清理目标。

1.20.1 还确认 `MiscData.serialize` 把目标 ID 写进外层 `tag`，`deserialize` 却从 `miscData` 子层读取；清理 `getTargetedByScepter().clear()` 又绕过封装的状态变更。这部分与 CE 修复可直接对应。

前三版使用 Citadel 的 `MiscProperties` 和不同的 NBT 数据布局，不能把 1.20.1 的层级补丁复制过去；需要分别适配使用结束和目标清理。会话内整数实体 ID 也不能直接作为跨重启的稳定身份。

### M10：同步与保存还有剩余价值

原版罐、精灵屋、底座等发送 `sendMSGToAll`，消息只携带坐标，接收端在当前世界查找同坐标 BE，仍有跨维度串状态和无关广播的问题。Patcher 的 `TileEntityJarMixin` 只增加初始同步数据，没有覆盖这些更新范围或标脏路径。

1.20.1 `TileEntityPodium.setItem` 把数据写入临时 NBT 后丢弃，没有直接标脏；`removeItemNoUpdate` 恒返回空栈。罐的产粉、收粉、释放和精灵屋进出也缺少一致的持久化通知。四版都有对应旧逻辑，适合统一修复，但应按各版本容器和 BE API 实现。

优先保留原版消息格式，缩小到同维度的实际跟踪者；若改成原版 BE 包，需要验证未装 Patcher 的客户端兼容性。释放精灵时要服务端执行并原子清空旧物品/主人状态，不能只添加 `setChanged`。

### M11/M12：最明确的客户端性能候选

四版图鉴的绘图和文字路径各有一次 `IOUtils.readLines`，资源流没有规范关闭，也没有按页面缓存。上游虽有图片 ResourceLocation 缓存，但文本读取未缓存，Patcher 尚未补上。可迁移按语言/页面缓存、try-with-resources、缺页回退和资源重载清缓存。缓存应保留现有文本/图片标记解析行为。

四版石像都在模型缓存检查前创建备用猪模型；1.18.2 以后每次还调用 `bakeLayer`，1.16.5 是直接构造模型。可在渲染器初始化时准备备用模型，避开逐帧创建。

四版 `hollowEntityMap` 都按被石化实体类型缓存假实体，仅首次加载 trapped NBT；同类不同变种/装备/头数的石像会串用状态。应按石像身份和 NBT 隔离缓存，并避免跨世界保留假实体。现有动画器引用清理 Mixin 不解决这些问题。

这些路径的重复工作已静态确认；本轮未测 FPS/MSPT，不能承诺固定百分比的收益。

### M13：重复碰撞是独立的小补丁

上游类名确实拼为 `EntityMutlipartPart`。四版 `tick` 都在慢跟随分支里查询/推挤一次，分支之后又调用一次 `collideWithNearbyEntities`；`EntitySlowPart` 使用该分支。1.20.1 对应 `:149` 和 `:161`。

可以精确删除第一次重复调用，保留更新完部件位置后的统一处理。需要测试普通部件和慢跟随部件的接触推挤，避免误删全部碰撞。它和 M01 的网络协议改动可分开实施。

## 不宜直接移植或已经覆盖的项目

- 精灵罐首次区块同步：1.18.2～1.20.1 已由 `TileEntityJarMixin` 和插件启用；1.16.5 上游自己实现 `getUpdateTag`。保留现有方案，不能算新补丁。
- 模型动画器持有实体引用、龙息距离和巡游高度、主菜单与 Citadel 启动：Patcher 已有对应实现。本轮没有把它们重复列为 CE 迁移收益，也未为其现有实现做完整回归验收。

## 建议实施顺序与集中验证

建议先落地 M01～M06，再补 M07～M13；M14 的召唤水晶独立安排。实现时按网络、锻炉、AI、客户端拆分补丁，便于隔离兼容问题，但不要求按每个报告编号创建独立配置。

遵循当前 Stonecutter 架构处理 1.16 与后续包名，以及实例 tick/静态 ticker、Random/RandomSource、配方签名的差异。现有 mixin 配置是 required 且 defaultRequire=1，必须核对每版实际声明/调用点；不能用宽泛 `require=0` 隐藏补丁未生效。新增客户端补丁只应在 client 列表或客户端插件分支中加载。

建议用以下集中场景验证，无需逐项重复建测试世界：

1. 四版分别编译并启动客户端、专服，检查 refmap、Mixin 应用数量及专服不加载客户端类。先以 1.20.1 验证功能，再向前三版适配；四版打包完成不代表四版游戏行为都验证。
2. 网络/菜单：双人乘骑、肩乘幼龙、各部件合法近战与交互、九头蛇断头、讲台正常解锁/离开距离/拆方块后的关闭；隔离开发服中测试越界编号和非法参数必须拒绝，同时验证原版客户端兼容。
3. 锻炉/BE：三种锻炉反复拆装并保留库存，停火降进度，长配方及不同 NBT 输出，换相邻核心；两维度相同坐标放罐/屋/底座，交互、卸载区块并重启，检查物品、主人和产粉状态。
4. AI/权杖：分多个 tick 生成不同 ID 的生物，再投食或靠近；覆盖三个蚁族 Goal、龙索敌/繁殖、精灵逃跑。两名玩家分别持续使用权杖、换栈和停用，检查耐久及目标独立。
5. 客户端/性能：图鉴连续停留、切页、切语言、F3+T；同屏多座同类不同 NBT 石像，换世界后重测；大量海蛇接触实体。对照相同场景记录资源读取/模型构造/碰撞调用次数，再按需做帧耗时或 MSPT 对比。

本轮实际完成的是源码/字节码静态核对、现有补丁覆盖排查和证据归档。未修改生产代码，因此没有构建新的补丁 JAR，也没有宣称上述回归场景已经通过。
